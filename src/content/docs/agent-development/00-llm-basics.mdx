## Concept 1: Token

LLMs don't read characters. They don't read words. They read **tokens** — small chunks of text that the model treats as atomic units.

A rough rule of thumb in English:

```
1 token  ≈  4 characters
1 token  ≈  ¾ of a word
100 tokens  ≈  75 words  ≈  1 short paragraph
```

So when you send the prompt:

```
"Book a flight from Paris to Tokyo on March 15"
```

The model sees roughly **12 tokens**, not 9 words. The exact split depends on the tokenizer, but the order of magnitude is what matters.

### Why you care

Three reasons, every one of which will return in this training:

1. **Cost** — You pay per token. Input tokens and output tokens are billed separately. A 1000-word document is ~1300 tokens of input.
2. **Speed** — More tokens = more compute = slower response. A 5-paragraph answer takes meaningfully longer than a 1-sentence one.
3. **Limits** — Models have a maximum number of tokens they can process at once (we'll meet this in the next concept).

<KeyInsight>
**Tokens are the unit of everything**: cost, speed, and capacity. When you start tuning agents in production, the first question is always "how many tokens did we burn?"
</KeyInsight>

## Concept 2: Context Window

Every LLM has a maximum amount of text it can "see" at one time. This is the **context window**, measured in tokens.

| Model | Context window |
|---|---|
| GPT-3.5 | 16K tokens (~12K words) |
| GPT-4o | 128K tokens (~96K words) |
| Claude Sonnet 4 | 200K tokens (~150K words) |
| Gemini 1.5 Pro | 1M tokens (~750K words) |

The context window includes **everything** the model sees in a single call:

This has one massive consequence: **the model has no memory between calls.** Every API call is stateless. If you want it to "remember" the previous conversation, you have to send the whole conversation back with every new message.

### The agent connection

This is exactly why Module 3 (LangChain Memory) and Module 4 (LangGraph State) exist. They're patterns for managing what gets sent in the context window, because:

- Sending the entire history every time → expensive, slow, eventually overflows
- Sending nothing → model has amnesia
- Sending a smart summary → the right answer

You'll see all three strategies before lunch.

## Concept 3: Temperature

Temperature controls **how creative** the LLM is when picking the next token. It's a number, usually between 0 and 1 (sometimes up to 2).

| Temperature | Behavior | When to use |
|---|---|---|
| **0** | Deterministic, picks the most likely token every time | Code generation, JSON output, tool calls, math |
| **0.3 – 0.5** | Slightly varied, mostly predictable | Customer support, document Q&A, summaries |
| **0.7 – 1.0** | Creative, varied outputs | Brainstorming, marketing copy, creative writing |
| **1.5 – 2.0** | Wild, often nonsensical | Almost never |

### The agent connection

In agent code, you'll see this constantly:

```python
llm = ChatGroq(model="llama-3.3-70b-versatile", temperature=0)
```

That `temperature=0` is not random. When an agent has to call a tool, you want it to **always** make the same decision for the same input. You don't want creativity in the middle of a payment flow. You want determinism.

When the agent is **drafting a customer email**, you might bump it to 0.5 — a bit of warmth without going off-script.

<KeyInsight>
**Default to temperature=0 for agents.** Bump it up only when the output is meant to feel human, not mechanical. Creativity is the wrong word — what you're really tuning is **predictability**.
</KeyInsight>

## Concept 4: Prompt

A **prompt** is the exact text you send to the LLM. That's the whole definition. Why we make a fuss about it: **small changes in the prompt produce large changes in the output.**

Compare these three prompts asking for the same thing:

<Tabs>
  <TabItem label="Vague">
    ```text
    Help me with flights.
    ```
    The model has no idea what you want. Will probably ask a clarifying question or generate something generic.
  </TabItem>

  <TabItem label="Specific">
    ```text
    I need to fly from Paris to Tokyo on March 15. 
    Suggest 3 flight options sorted by price.
    ```
    The model knows the task. Will produce 3 fictional options unless you give it real data.
  </TabItem>

  <TabItem label="Specific + Constraint">
    ```text
    You are a flight assistant. The user wants to fly from Paris (CDG) 
    to Tokyo (HND) on 2025-03-15. 
    
    Use the search_flights tool to find real options.
    Return exactly 3 results, sorted by price.
    Format as a numbered list with: airline, price, duration.
    ```
    The model knows: its role, the exact task, what tool to call, the format, and the count. This is the kind of prompt agents use under the hood.
  </TabItem>
</Tabs>

### The agent connection

Almost every framework you'll see today (LangChain, LangGraph, MCP) is in some way a **structured way to build prompts**. They give you:

- **Templates** — fill-in-the-blanks for the user input
- **Roles** — system / user / assistant / tool message types
- **Composition** — chaining prompts together with the output of previous steps

When something goes wrong with an agent, the first thing you do is **print the prompt** and read it. 90% of the time, the bug is in there.

<KeyInsight>
**Prompts are the source code of LLM behavior.** Treat them with the same care you'd treat a function signature: be explicit about inputs, outputs, constraints, and intent.
</KeyInsight>

## Putting It Together

Every LLM call you'll see today combines all four:

```python
llm = ChatGroq(
    model="llama-3.3-70b-versatile",
    temperature=0,                    # ← Concept 3
)

prompt = """You are a flight assistant.   ← Concept 4
Use the search_flights tool when asked about availability.
"""                                    # ← consumes tokens (1)
                                        # ← all of this lives inside
                                        #    the context window (2)

response = llm.invoke(prompt + user_message)
```

That's it. Four words, one mental model. We're ready for agents.

<DeepDive title="Bonus: Streaming">

Most LLM APIs support **streaming** — receiving the output token by token instead of all at once. The total cost and total time are roughly the same, but the *perceived* speed is much better, because the user sees the first word in 100ms instead of waiting 5 seconds for the whole thing.

```python
# Non-streaming: wait for the full answer
response = llm.invoke("Explain RAG")  # 5 seconds of silence

# Streaming: tokens arrive as they're generated
for chunk in llm.stream("Explain RAG"):
    print(chunk.content, end="", flush=True)  # types out live
```

In agent code, streaming matters when there's a human watching. For backend pipelines (no human in the loop), batch responses are simpler. We'll mention this once or twice in later modules but won't dwell on it.

</DeepDive>

<DeepDive title="Bonus: How Tokens Map to Cost">

Every API has a price per million tokens, with different rates for input and output. Example, for a typical mid-tier model:

| Item | Tokens | Rate | Cost |
|---|---|---|---|
| User message | 50 | $0.50/M | $0.000025 |
| System prompt + history | 1500 | $0.50/M | $0.00075 |
| Generated response | 300 | $1.50/M | $0.00045 |
| **Total per call** | 1850 | — | **~$0.0012** |

Looks tiny. Multiply by 10,000 user requests per day → $12/day → $360/month. Multiply by complex agent workflows that make 5–10 LLM calls per user request → $1,800–$3,600/month. That's why Module 5 has a "Cost Control" section.

</DeepDive>

## Recap (in 30 seconds)

1. **Token** — the unit of text the model sees. Drives cost, speed, and limits.
2. **Context window** — the maximum amount of text per call. Includes system prompt, history, retrieved docs, and current input.
3. **Temperature** — predictability dial. 0 for tools and code, higher for human-feeling text.
4. **Prompt** — the exact text you send. Small changes = large output differences. Treat it like source code.
