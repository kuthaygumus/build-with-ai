## Concept 1: Token

LLMs don't read characters. They don't read words. They read **tokens** — small chunks of text that the model treats as atomic units.

A rough rule of thumb in English:

```
1 token  ≈  4 characters
1 token  ≈  ¾ of a word
100 tokens  ≈  75 words  ≈  1 short paragraph
```

So a 1000-word document is **~1300 tokens**. A 100-page PDF is **~50,000 tokens**.

### Why you care for RAG

Three reasons that will define every chunking and indexing decision later today:

1. **Embedding models have token limits** — the most common embedding model accepts max 512 tokens per chunk. That's why you can't just embed an entire document; you have to split it.
2. **LLM context windows are finite** — even if you retrieve 50 relevant docs, they all have to fit inside the LLM's token budget alongside the user's question.
3. **Cost is per token** — both for embedding (cheap) and generation (expensive). A chatty RAG system can burn money fast.

<KeyInsight>
**Tokens drive every RAG design decision.** Chunk size, retrieval count (k), context budget — they're all token math under the hood.
</KeyInsight>

## Concept 2: Context Window

Every LLM has a maximum amount of text it can "see" at one time. This is the **context window**, measured in tokens.

| Model | Context window |
|---|---|
| GPT-3.5 | 16K tokens (~12K words) |
| GPT-4o | 128K tokens (~96K words) |
| Claude Sonnet 4 | 200K tokens (~150K words) |
| Gemini 1.5 Pro | 1M tokens (~750K words) |

In RAG, the context window has a very specific job: **it holds the retrieved documents plus the user's question plus the system prompt**, all at once.

This is why RAG isn't just "throw everything at the LLM". You retrieve **only the most relevant** few chunks, fit them in the budget, and let the model focus.

### The RAG connection

When you tune `k=5` (retrieve top 5 chunks) instead of `k=20`, you're managing the context window. When you choose chunk_size=500 vs chunk_size=2000, you're managing the context window. Every parameter you'll see in Module 3 is, deep down, a context window decision.

## Concept 3: Vector

This is the one that scares most people. It shouldn't.

A **vector** is a list of numbers. That's it. The whole definition.

```python
vector = [0.12, -0.34, 0.87, 0.04, -0.56, 0.23, ...]
```

In RAG, these vectors usually have **384, 768, or 1536 numbers** in them (depending on the embedding model). Each number is called a **dimension**.

Why so many dimensions? Because each one captures some subtle aspect of meaning. One dimension might encode "is this about animals?", another "is this formal or casual?", another "is this asking a question or making a statement?". You don't get to see what each dimension means — the model learns them on its own — but together they paint a very rich picture of what a piece of text *is about*.

<KeyInsight>
**A vector is just a list of numbers that represents meaning.** The model doesn't store words — it stores positions in a high-dimensional space where similar meanings live close together.
</KeyInsight>

### A picture helps

Imagine a 2D map (just to make it visual — real vectors have 1000+ dimensions):

```
                    politics  ●
                    
                                          economics  ●
                    
        cooking ●
                                                   business  ●
                    recipes  ●
                    
                                food ●
```

Texts about cooking sit close to each other. Texts about business sit close to each other. Cooking and business sit far apart. **That's all vectors do.** They turn text into coordinates so we can measure "are these about the same thing?" with simple math.

## Concept 4: Similarity

Once you have two vectors, you measure how close they are. Close = similar meaning. Far = different meaning.

The most common math is **cosine similarity**, which gives you a number between -1 and 1:

| Cosine | Meaning |
|---|---|
| **1.0** | Identical |
| **0.9 – 1.0** | Almost the same thing |
| **0.7 – 0.9** | Related, same topic |
| **0.4 – 0.7** | Loosely related |
| **0.0** | Unrelated |
| **< 0.0** | Opposite meaning (rare in practice) |

You don't need to remember the formula. You just need to remember: **higher cosine = more similar**.

### The RAG connection

When you call `vector_store.similarity_search(query, k=5)`, this is what happens under the hood:

1. The query gets converted to a vector
2. The system computes cosine similarity between the query vector and **every** vector in the database
3. It returns the **5 vectors with the highest similarity scores**
4. Those vectors map back to text chunks → handed to the LLM

That's the whole "magic" of semantic search. No keyword matching. No SQL. Just: which stored texts are closest in meaning to this question?

<KeyInsight>
**Similarity = the math behind "find me chunks that mean the same thing".** You don't need to compute it by hand — the vector store does it for you. You just need to know what the score means.
</KeyInsight>

## Concept 5: Embedding

How does a piece of text *become* a vector? Through an **embedding model** — a special kind of LLM whose only job is "text in, vector out".

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer('all-MiniLM-L6-v2')

vector = model.encode("Flight delayed at CDG")
# → [0.12, -0.34, 0.87, ..., 0.04]    (384 numbers)
```

Embedding models are trained on huge amounts of text so that:

- "Flight delayed at CDG" and "CDG flight is late" produce **very similar** vectors
- "Flight delayed at CDG" and "Pizza recipe ideas" produce **very different** vectors

That's it. The model learns to encode meaning into geometry. You feed text in, you get a vector out, you can compare that vector to others.

### Embedding model vs LLM

Both are neural networks. Both deal with text. They have very different jobs:

| | Embedding model | LLM (chat model) |
|---|---|---|
| **Input** | Text | Text |
| **Output** | A vector | Text |
| **Used for** | Search, similarity, clustering | Generation, reasoning, conversation |
| **Examples** | `text-embedding-3-small`, `all-MiniLM-L6-v2` | GPT-4, Claude, Llama 3 |
| **Cost** | Very cheap | Expensive |

In a RAG system, **you use both**: the embedding model for the search step, the LLM for the generation step. They're complementary, not competitors.

<KeyInsight>
**An embedding is what an embedding model produces when you give it text.** Text in → vector out. That vector is your address in the meaning-space.
</KeyInsight>

## Putting It Together

Here's how all five concepts fit into a single RAG flow:

```python
# 1. Indexing (offline, once)
chunks = split_document("flight-policy.pdf", chunk_size=500)  # ← Concept 1 (tokens)
vectors = embedding_model.encode(chunks)                       # ← Concepts 3, 5
vector_store.add(vectors, chunks)

# 2. Querying (online, every request)
query = "What's the rebooking policy for cancelled flights?"
query_vector = embedding_model.encode(query)                   # ← Concept 5

results = vector_store.similarity_search(query_vector, k=5)   # ← Concept 4
context = "\n\n".join(results)                                 # ← Concept 1 (token budget)

answer = llm.invoke(f"""Answer using this context only:
{context}

Question: {query}""")                                          # ← Concept 2 (context window)
```

Five concepts. One pipeline. We're ready for the rest of the day.

<DeepDive title="Bonus: Why 1536 dimensions?">

It's not magic — it's an architectural choice. Different embedding models use different vector sizes:

| Model | Dimensions | Notes |
|---|---|---|
| `all-MiniLM-L6-v2` | 384 | Small, fast, free, runs locally |
| `all-mpnet-base-v2` | 768 | Mid-size, better quality |
| `text-embedding-3-small` | 1536 | OpenAI, paid, very high quality |
| `text-embedding-3-large` | 3072 | OpenAI, biggest, most expensive |

More dimensions = more nuance captured = better similarity precision = more storage and slower comparisons. There's no universal "right" size. For most production RAG systems, 384 to 1536 is the sweet spot.

You don't pick a vector size; you pick a model, and the model defines its size.

</DeepDive>

<DeepDive title="Bonus: A note on temperature for RAG">

Temperature is the LLM setting that controls how random the model's output is (0 = deterministic, 1 = creative). In RAG, you almost always want **temperature=0** for the generation step because:

- You're answering from retrieved facts, not improvising
- You want the same input to produce the same output (testable, debuggable)
- Creativity in a RAG system is usually a hallucination in disguise

The Agent Development course goes deeper on temperature. For RAG, just remember: keep it at 0 unless you have a specific reason not to.

</DeepDive>

## Recap (in 30 seconds)

1. **Token** — the unit of text. Drives chunk size, retrieval count, and cost.
2. **Context window** — the budget for what fits in one LLM call. RAG retrieves to fit this budget.
3. **Vector** — a list of numbers that represents meaning. Usually 384–1536 numbers.
4. **Similarity** — math that compares two vectors. Higher cosine = more similar meaning.
5. **Embedding** — what an embedding model produces. Text in, vector out.
