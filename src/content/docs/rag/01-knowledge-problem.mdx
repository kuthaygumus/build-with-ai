## Why LLMs Fail at Enterprise Knowledge

LLMs have three fundamental blind spots. Each one is a blocker for enterprise use. RAG addresses all three.

### 1. Hallucination

LLMs don't "know" things. They predict the next token. When training data is sparse on a topic, they fill the gap with plausible-sounding fiction.

```python
# Ask about a specific Flight API version
response = llm("What are the parameters for the FlightOffers v4 API?")
# The LLM will confidently describe parameters that don't exist,
# mixing real v2 params with invented ones.
# It doesn't know the difference. It can't.
```

### 2. Stale Knowledge

Every model has a training cutoff. The world keeps moving. The model doesn't.

Your internal docs change daily. Retraining costs GPU-weeks and six figures. That's not a workflow — that's a crisis.

### 3. Zero Access to Private Data

LLMs are trained on the public internet. They have **zero knowledge** of your internal wikis, customer contracts, GDS documentation, incident reports, or architecture decisions.

This isn't a model quality problem. GPT-5 won't fix it. Claude 4 won't fix it. **It's an architecture problem.** RAG is the architecture solution.

## What Is RAG — In 30 Seconds

**Retrieval-Augmented Generation.** Instead of relying on what the model "remembers" from training, you retrieve relevant documents and inject them into the prompt.

The model reads your docs, then answers. Every time. Fresh data. Cited sources.

The key insight: **the LLM never sees your entire knowledge base.** It sees only the few most relevant chunks, injected alongside the question.

```python
# RAG in 10 lines of pseudocode
def rag_answer(question: str) -> str:
    # 1. Find relevant documents
    relevant_docs = vector_store.similarity_search(question, k=5)

    # 2. Build prompt with context
    context = "\n\n".join([doc.page_content for doc in relevant_docs])
    prompt = f"""Answer based ONLY on this context. If unsure, say so.

Context:
{context}

Question: {question}"""

    # 3. Generate grounded answer
    return llm.invoke(prompt)
```

## RAG vs Fine-Tuning

This is the question everyone asks. Here's the decision:

| | RAG | Fine-Tuning |
|---|---|---|
| **Purpose** | Model needs to **know** something | Model needs to **behave** differently |
| **Data freshness** | Real-time (re-index anytime) | Stale (requires retraining) |
| **Source attribution** | Built-in (you know which doc) | Not possible |
| **Cost** | Low (embedding + storage) | High (GPU hours) |
| **Hallucination control** | Strong (grounded in sources) | Weak (still generates freely) |
| **Best for** | Knowledge retrieval, Q&A, search | Tone, format, domain language |

<KeyInsight>
Use RAG when you need the model to **know** something. Use fine-tuning when you need the model to **behave** differently. In production, you often use both.
</KeyInsight>

## The Indexing Phase — What Happens Before Queries

Before RAG can answer anything, you prepare your knowledge base. This happens offline, once:

<FlowDiagram title="Offline Indexing Pipeline">
  <div class="flow-row">
    <div class="flow-node secondary">
      <span class="node-icon">📄</span>
      <span class="node-label">Load</span>
      <span class="node-desc">PDF, web, markdown, API</span>
    </div>
    <div class="flow-arrow animated">→</div>
    <div class="flow-node secondary">
      <span class="node-icon">✂️</span>
      <span class="node-label">Chunk</span>
      <span class="node-desc">Split into focused passages</span>
    </div>
    <div class="flow-arrow animated">→</div>
    <div class="flow-node secondary">
      <span class="node-icon">🧮</span>
      <span class="node-label">Embed</span>
      <span class="node-desc">Convert text to vectors</span>
    </div>
    <div class="flow-arrow animated">→</div>
    <div class="flow-node success">
      <span class="node-icon">💾</span>
      <span class="node-label">Store</span>
      <span class="node-desc">Save in vector database</span>
    </div>
  </div>
</FlowDiagram>

```python
from langchain_community.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma

# 1. Load
docs = PyPDFLoader("flight-api-guide.pdf").load()

# 2. Chunk
chunks = RecursiveCharacterTextSplitter(
    chunk_size=1000, chunk_overlap=200
).split_documents(docs)

# 3. Embed + Store
vector_store = Chroma.from_documents(
    documents=chunks,
    embedding=OpenAIEmbeddings(model="text-embedding-3-small"),
    persist_directory="./chroma_db"
)

print(f"Indexed {len(chunks)} chunks from {len(docs)} pages")
```

We'll dive deep into each step in the coming modules. For now, remember the flow: **Load, Chunk, Embed, Store.**

<DeepDive title="The Academic Origins of RAG">

RAG was introduced in the 2020 paper **"Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks"** by Patrick Lewis et al. at Facebook AI Research.

The key contribution: combine a pre-trained seq2seq model (BART) with a dense retriever (DPR), trained end-to-end. The retriever and generator jointly optimize what to retrieve and how to generate.

Modern RAG has diverged significantly. Today's systems use frozen LLMs (no end-to-end training), vector databases instead of FAISS, and prompt engineering instead of fine-tuned generators. The term "RAG" has evolved from a specific architecture to a **design pattern** — any system that retrieves external knowledge to augment generation.

**Key papers in the RAG lineage:**
1. **DPR** (Karpukhin et al., 2020) — Dense Passage Retrieval
2. **RAG** (Lewis et al., 2020) — The original paper
3. **RETRO** (Borgeaud et al., 2022) — Retrieval-enhanced transformers at scale
4. **Self-RAG** (Asai et al., 2023) — LLM decides when to retrieve
5. **CRAG** (Yan et al., 2024) — Corrective RAG with retrieval evaluation

</DeepDive>

## What to Take Away

Three things:

1. **LLMs have three blind spots** — hallucination, stale knowledge, no private data. RAG fixes all three, not by changing the model, but by changing the input.

2. **RAG = retrieve, then generate.** Find the relevant documents, inject them into the prompt, let the model answer from evidence. Simple concept, powerful results.

3. **RAG vs fine-tuning is not a competition.** RAG is for knowledge. Fine-tuning is for behavior. Know which problem you're solving.
