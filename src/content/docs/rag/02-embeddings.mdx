## What Are Embeddings, Concretely

An embedding is a list of numbers. Typically 768 to 3072 of them. Each sentence becomes one vector:

```python
from openai import OpenAI

client = OpenAI()
response = client.embeddings.create(
    model="text-embedding-3-small",
    input="The flight from CDG to NRT was delayed 3 hours"
)

vector = response.data[0].embedding
print(f"Dimensions: {len(vector)}")   # 1536
print(f"First 5 values: {vector[:5]}")  # [0.012, -0.034, 0.087, ...]
```

Two sentences about flight delays will produce vectors that are **close together** in 1536-dimensional space. A sentence about chocolate cake will be **far away**. That closeness is measurable — and that's what makes retrieval work.

## Similarity Metrics

Once you have vectors, you need to measure how close they are. Three approaches, one winner.

### Cosine Similarity — The Default

Measures the **angle** between two vectors. Ignores magnitude, focuses on direction.

```python
import numpy as np

def cosine_similarity(a: np.ndarray, b: np.ndarray) -> float:
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

# Flight delay vectors — similar meaning
vec_delay = np.array([0.12, -0.34, 0.87])
vec_late  = np.array([0.11, -0.32, 0.85])

# Chocolate cake vector — different meaning
vec_cake  = np.array([0.78,  0.56, -0.12])

print(cosine_similarity(vec_delay, vec_late))   # 0.999 — almost identical
print(cosine_similarity(vec_delay, vec_cake))   # 0.12  — completely different
```

**Range**: -1 (opposite meaning) to +1 (identical meaning). This is what you'll use 90% of the time.

### Dot Product and Euclidean Distance

| Metric | What It Measures | When to Use |
|--------|-----------------|-------------|
| **Cosine Similarity** | Angle between vectors | Default for text. Most embedding models normalize vectors, making this equivalent to dot product. |
| **Dot Product** | Projection of one vector onto another | When magnitude matters (relevance scoring). Faster to compute. |
| **Euclidean Distance** | Straight-line distance | Low-dimensional spaces, clustering. Less common for text. |

<Aside type="tip">
OpenAI's embedding models produce **normalized vectors** — meaning cosine similarity and dot product give identical rankings. Use whichever your vector database optimizes for.
</Aside>

## Vector Databases — Why You Need Them

"Can't I just store embeddings in Postgres and calculate similarity?"

Technically yes. At 1 million documents with 1536 dimensions, that's 1.5 billion floating-point comparisons per query. Response time: seconds. Unacceptable.

Vector databases use **Approximate Nearest Neighbor (ANN)** algorithms to search billions of vectors in milliseconds. They trade a tiny amount of accuracy for massive speed.


**Best for**: Prototyping, learning, small-to-medium datasets. Open-source, embedded, no server needed.
  </TabItem>

  <TabItem label="pgvector">
```sql
-- Enable the extension
CREATE EXTENSION vector;

-- Create table with vector column
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    content TEXT,
    source TEXT,
    embedding vector(1536)
);

-- Create ANN index
CREATE INDEX ON documents
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

-- Semantic search
SELECT content, source,
       1 - (embedding <=> query_embedding) AS similarity
FROM documents
ORDER BY embedding <=> query_embedding
LIMIT 5;
```

**Best for**: Teams already on PostgreSQL. Production-ready, familiar tooling, SQL interface.
  </TabItem>

  <TabItem label="Pinecone">
```python
from pinecone import Pinecone

pc = Pinecone(api_key="your-api-key")

pc.create_index(
    name="travel-docs",
    dimension=1536,
    metric="cosine",
    spec={"serverless": {"cloud": "aws", "region": "us-east-1"}}
)

index = pc.Index("travel-docs")

# Query with metadata filtering
results = index.query(
    vector=[0.11, -0.32, ...],
    top_k=5,
    filter={"category": {"$eq": "flights"}},
    include_metadata=True
)
```

**Best for**: Fully managed, serverless, enterprise scale. No infrastructure to manage.

### Quick Comparison

| Feature | Chroma | pgvector | Pinecone |
|---------|--------|----------|----------|
| **Type** | Embedded | PostgreSQL extension | Managed cloud |
| **Setup** | `pip install` | PostgreSQL + extension | API key |
| **Scale** | ~100K docs | ~10M docs | Billions |
| **Cost** | Free | Free (your DB) | Pay-per-use |
| **Best for** | Dev/learning | Existing Postgres | Enterprise |

<DeepDive title="ANN Algorithms — HNSW, IVF, and Quantization">

Vector databases don't do brute-force comparison. They use Approximate Nearest Neighbor algorithms that trade a small amount of recall for enormous speed.

### HNSW (Hierarchical Navigable Small World)

The most popular algorithm. Builds a multi-layered graph — sparse connections at the top for fast coarse search, dense connections at the bottom for precise local search. Search starts at the top and navigates down.

**Key parameters:**
- `M` — max connections per node (higher = better recall, more memory)
- `ef_construction` — search width during build (higher = better index, slower build)
- `ef_search` — search width during query (higher = better recall, slower query)

```python
# Chroma uses HNSW by default
collection = client.create_collection(
    name="my_collection",
    metadata={
        "hnsw:M": 32,                # default: 16
        "hnsw:construction_ef": 200,  # default: 100
        "hnsw:search_ef": 100         # default: 10
    }
)
```

### IVF (Inverted File Index)

Partitions the vector space into clusters. At query time, only searches the nearest clusters instead of the entire space.

### Product Quantization (PQ)

Compresses vectors to reduce memory. Splits each vector into sub-vectors and quantizes each independently. Memory reduction: **32x** with minimal quality loss.

### Performance

| Algorithm | Query Time | Memory | Recall@10 |
|-----------|-----------|--------|-----------|
| Brute Force | O(n) | 1x | 100% |
| IVF | O(n/k) | 1x | ~95% |
| HNSW | O(log n) | 1.5x | ~99% |
| IVF + PQ | O(n/k) | 0.03x | ~90% |

Most vector databases default to HNSW — best recall-to-speed trade-off.

</DeepDive>

## What to Take Away

Three things:

1. **Embeddings turn meaning into math.** Similar text produces nearby vectors. Different text produces distant vectors. This is the entire mechanism behind RAG retrieval.

2. **Cosine similarity is your default metric.** It measures the angle between vectors, ignoring magnitude. Works with every major embedding model.

3. **Vector databases make this scale.** ANN algorithms like HNSW let you search millions of vectors in milliseconds. Start with Chroma for learning, migrate to pgvector or Pinecone for production.
