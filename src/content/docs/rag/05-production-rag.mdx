## Evaluation with RAGAS

You can't improve what you can't measure. **RAGAS** (Retrieval Augmented Generation Assessment) is the standard framework for evaluating RAG systems.

| Metric | What It Asks | Low Score Means |
|--------|-------------|-----------------|
| **Context Precision** | Are the retrieved chunks relevant? | Too much noise in retrieval. Reduce k or add re-ranking. |
| **Context Recall** | Did we find all needed information? | Missing relevant docs. Improve chunking or add multi-query. |
| **Faithfulness** | Is the answer supported by the context? | Model is hallucinating beyond the context. Fix the prompt. |
| **Answer Relevancy** | Does the answer address the question? | Model is going off-topic. Focus the system prompt. |

### Implementation

```python
from ragas import evaluate
from ragas.metrics import (
    faithfulness,
    answer_relevancy,
    context_precision,
    context_recall,
)
from datasets import Dataset

eval_data = {
    "question": [
        "How do I authenticate with the Flight Offers API?",
        "What is the baggage allowance for economy?",
        "Can I modify a booking after ticketing?"
    ],
    "answer": [
        "Use OAuth 2.0 client credentials flow with /v1/security/oauth2/token.",
        "Economy baggage allowance is typically 23kg for checked bags.",
        "Yes, modifications are possible through the Booking Management API."
    ],
    "contexts": [
        ["The Flight API uses OAuth 2.0. Send credentials to /v1/security/oauth2/token..."],
        ["Baggage policies vary by airline. Standard economy: 23kg checked, 8kg carry-on..."],
        ["Post-ticketing changes require the Booking Management API. Some changes incur fees..."]
    ],
    "ground_truth": [
        "OAuth 2.0 client credentials flow via /v1/security/oauth2/token endpoint.",
        "23kg for checked luggage, varies by airline and fare class.",
        "Yes, via Booking Management API, subject to airline rules and possible fees."
    ]
}

results = evaluate(
    Dataset.from_dict(eval_data),
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
)
print(results)
# {'faithfulness': 0.92, 'answer_relevancy': 0.88,
#  'context_precision': 0.65, 'context_recall': 0.90}
```

### Reading the Scores

```text

Context Precision:  0.65  — Too many irrelevant chunks retrieved
Context Recall:     0.90  — Important info is being found

Diagnosis: Retrieval finds the right stuff but also too much noise.
Action: Add re-ranking or reduce k.
```

## Production Pitfalls

Three patterns that kill production RAG systems. Each has a specific fix.

### Pitfall 1: Lost in the Middle

LLMs pay more attention to the **beginning and end** of the context. If the critical chunk is in the middle, it might be ignored.

<FlowDiagram title="Lost in the Middle">
  <div class="flow-row">
    <div class="flow-node success">
      <span class="node-icon">👁️</span>
      <span class="node-label">Chunk 1</span>
      <span class="node-desc">LLM pays attention</span>
    </div>
    <div class="flow-arrow">→</div>
    <div class="flow-node danger">
      <span class="node-icon">😶</span>
      <span class="node-label">Chunk 3: THE ANSWER</span>
      <span class="node-desc">LLM might miss this!</span>
    </div>
    <div class="flow-arrow">→</div>
    <div class="flow-node success">
      <span class="node-icon">👁️</span>
      <span class="node-label">Chunk 5</span>
      <span class="node-desc">LLM pays attention</span>
    </div>
  </div>
</FlowDiagram>

**Fixes**: Reduce k (fewer chunks = less "middle"), re-rank so best chunk is always first, or use the bookend pattern — place the most relevant chunks at positions 1 and last.

### Pitfall 2: Conflicting Sources

Your knowledge base contains a 2023 doc saying "rate limit: 100/min" and a 2024 doc saying "500/min." RAG retrieves both. LLM picks one at random.

**Fixes**: Add `version` and `date` metadata, filter for latest during retrieval, include "prefer the most recent source" in the prompt, and remove outdated docs during indexing.

```python
# Metadata-aware retrieval
results = vector_store.similarity_search(
    "rate limit for flight API",
    k=5,
    filter={"version": "v2"}  # only latest
)
```

### Pitfall 3: Over-Retrieval

Retrieving 20 chunks when only 2 are relevant. The signal drowns in noise.

**Fixes**: Retrieve broadly (k=20), then re-rank and keep top 5. Or use MMR for diverse, relevant results.

```python
# Retrieve 20, re-rank, keep 5
from langchain.retrievers import ContextualCompressionRetriever
from langchain_cohere import CohereRerank

retriever = ContextualCompressionRetriever(
    base_compressor=CohereRerank(top_n=5),
    base_retriever=vector_store.as_retriever(search_kwargs={"k": 20})
)
```

## Scaling for Production

### Multi-Level Caching

Cache at three levels to avoid redundant computation:

```python
from cachetools import TTLCache

# Level 1: Don't re-embed the same query
embedding_cache = TTLCache(maxsize=5000, ttl=86400)  # 24h

# Level 2: Same query = same retrieved chunks
retrieval_cache = TTLCache(maxsize=1000, ttl=3600)   # 1h

# Level 3: Exact same question = same answer
answer_cache = TTLCache(maxsize=500, ttl=1800)       # 30min
```

### Async Processing

Don't block on sequential operations. Run dense and sparse retrieval in parallel:

```python
import asyncio

async def async_rag(question: str) -> dict:
    # Dense + sparse retrieval in parallel
    dense_task = asyncio.create_task(
        vector_store.asimilarity_search(question, k=10)
    )
    sparse_task = asyncio.create_task(
        bm25_retriever.ainvoke(question)
    )
    dense_results, sparse_results = await asyncio.gather(dense_task, sparse_task)

    # Merge, re-rank, generate
    all_results = dense_results + sparse_results
    reranked = reranker.compress_documents(all_results, question)
    answer = await llm.ainvoke(prompt.format(
        context="\n\n".join(d.page_content for d in reranked[:5]),
        question=question
    ))
    return {"answer": answer.content, "sources": reranked[:5]}
```

### Cost Optimization

| Component | Cost Driver | Optimization |
|-----------|------------|--------------|
| **Embedding** | Tokens embedded | Use `text-embedding-3-small` ($0.02/1M) over `large` ($0.13/1M) |
| **LLM** | Context tokens | Reduce k, compress context, use `gpt-4o-mini` for simple queries |
| **Vector DB** | Storage + queries | Dimension reduction, quantization |
| **Re-ranking** | API calls | Only re-rank when initial confidence is low |

```python
# Cost-aware model routing
def choose_model(context_length: int) -> str:
    if context_length < 2000:
        return "gpt-4o-mini"   # $0.15/1M input tokens
    return "gpt-4o"             # $2.50/1M — handles long context better
```

## Monitoring

Track what matters in production:

```python
class RAGMonitor:
    def track_query(self, question: str, rag_fn):
        start = time.time()
        result = rag_fn(question)
        latency = time.time() - start

        self.log({
            "question": question,
            "latency_ms": latency * 1000,
            "num_chunks": len(result.get("sources", [])),
            "model": result.get("model", "unknown"),
        })

        if latency > 5.0:
            logger.warning(f"High latency: {latency:.1f}s for: {question[:50]}")
```

```python
def collect_feedback(query_id: str, helpful: bool, comment: str = ""):
```

## Multi-Tenant Architecture

In enterprise, different users see different documents. Enforce this at the **retrieval** level, not the generation level.

```python
class MultiTenantRetriever:
    def retrieve(self, query: str, user_id: str, user_roles: list[str]):
        return self.vector_store.similarity_search(
            query,
            k=10,
            filter={
                "$or": [
                    {"access": "public"},
                    {"owner": user_id},
                    {"allowed_roles": {"$in": user_roles}},
                ]
            }
        )
```

<Aside type="caution">
**Security**: Always filter at retrieval, not generation. If a restricted document makes it into the LLM context, the model might reveal it regardless of system prompt instructions. The context window is the trust boundary.
</Aside>

<DeepDive title="Advanced RAG Architecture Patterns at Scale">

### Pattern 1: Router RAG

Route queries to specialized pipelines based on domain:

```python
router_prompt = """Classify: flights, hotels, payments, or general.
Query: {query}
Category:"""

pipelines = {
    "flights": flight_rag_chain,
    "hotels": hotel_rag_chain,
    "payments": payment_rag_chain,
    "general": general_rag_chain,
}

category = llm.invoke(router_prompt.format(query=question)).strip()
answer = pipelines[category].invoke(question)
```

### Pattern 2: Corrective RAG (CRAG)

After retrieval, evaluate whether the documents are actually relevant. If not, fall back to web search or acknowledge ignorance:

```python
def corrective_rag(question: str) -> str:
    docs = retriever.invoke(question)
    score = evaluate_relevance(question, docs)  # LLM-as-judge

    if score >= 4:
        return generate_from_context(question, docs)
    elif score >= 2:
        web_docs = web_search(question)
        return generate_from_context(question, docs + web_docs)
    else:
        return "I don't have reliable information for this question."
```

### Pattern 3: Self-Reflective RAG

Generate, then critique, then refine. Loop until the answer is fully supported:

```python
def self_reflective_rag(question: str, max_iterations: int = 3) -> str:
    for i in range(max_iterations):
        docs = retriever.invoke(question)
        answer = generate_from_context(question, docs)
        critique = llm.invoke(f"Is this answer fully supported by context? {answer}")

        if "fully supported" in critique.content.lower():
            return answer
        question = llm.invoke(f"Refine query based on: {critique.content}").content

    return answer  # best effort
```

These patterns compose. A Router RAG where each sub-pipeline uses Corrective RAG with Self-Reflection. Architecture follows requirements: accuracy needs, latency budget, cost constraints.

</DeepDive>
