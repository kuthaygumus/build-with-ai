## The Integration Explosion

You have 5 AI applications — Claude, ChatGPT, Cursor, your custom app, a CI bot. They need to reach 8 tools — Jira, GitHub, Slack, PostgreSQL, Confluence, S3, email, a flight API.

Without a standard: **5 x 8 = 40 custom integrations.** Each with its own auth, data format, error handling, docs, and maintenance. Add one new tool? Five more integrations. Add one new AI client? Eight more.

## What Is MCP?

<Aside type="note" title="Official Definition">
**MCP (Model Context Protocol)** is an open standard for connecting AI applications to external data sources and tools. Think of MCP like a USB-C port for AI applications — just as USB-C provides a standardized way to connect devices, MCP provides a standardized way to connect AI to external systems.

— [modelcontextprotocol.io](https://modelcontextprotocol.io/docs/getting-started/intro)
</Aside>

MCP was created by Anthropic and open-sourced in late 2024. It's already adopted across the industry:

| Client | Status |
|---|---|
| **Claude Desktop / Claude Code** | Built-in MCP support |
| **ChatGPT** | MCP support (2025) |
| **VS Code (GitHub Copilot)** | MCP support |
| **Cursor** | MCP support |
| **Zed, Windsurf** | MCP support |

Build your tool once as an MCP server → it works with all of them. Build your client once with MCP support → it works with every tool.

<KeyInsight>
MCP turns 40 custom integrations into 13. Build once, connect everywhere. This is not a bet on a future standard — it's already the industry standard.
</KeyInsight>

## Architecture: Three Layers

MCP has a layered architecture — separation of concerns for security.

<FlowDiagram title="MCP Architecture">
  <div class="flow-row">
    <div class="flow-node secondary">
      <span class="node-icon">🏠</span>
      <span class="node-label">Host</span>
      <span class="node-desc">Claude Desktop, Cursor, your app</span>
    </div>
    <div class="flow-arrow animated">→</div>
    <div class="flow-node secondary">
      <span class="node-icon">📡</span>
      <span class="node-label">Client</span>
      <span class="node-desc">1:1 connection to a server</span>
    </div>
    <div class="flow-arrow animated">→</div>
    <div class="flow-node secondary">
      <span class="node-icon">⚡</span>
      <span class="node-label">Server</span>
      <span class="node-desc">Wraps an external tool</span>
    </div>
  </div>
</FlowDiagram>

<Steps>
1. **Host** — The application the user interacts with. Manages security, user consent, and spawns clients. Examples: Claude Desktop, Cursor, your custom agent.

2. **Client** — Lives inside the host. Each client has a 1:1 connection to a single server. If one server crashes, the others keep running. **Isolation by design.**

3. **Server** — Exposes capabilities (tools, resources, prompts) over the protocol. Wraps an external system and makes it accessible to AI in a standardized way.
</Steps>

Why three layers instead of two? **Security.** The host controls what the AI can access. The client provides isolation — a broken server can't poison the others. The server runs sandboxed, exposing only what it was designed to.

## Transport: How Messages Move

MCP uses JSON-RPC 2.0 for message format — the transport is pluggable:

<Tabs>
  <TabItem label="stdio (Local)">
    The server runs as a **child process**. Communication over stdin/stdout.

    ```json
    {
      "mcpServers": {
        "flight-data": {
          "command": "python",
          "args": ["flight_mcp_server.py"]
        }
      }
    }
    ```

    **Best for**: Local development, CLI tools, personal automation.
  </TabItem>

  <TabItem label="Streamable HTTP (Remote)">
    The server runs as a **web service**. HTTP for requests, optional SSE for streaming.

    ```json
    {
      "mcpServers": {
        "flight-data": {
          "url": "https://mcp.internal.example.com/flights",
          "headers": {
            "Authorization": "Bearer ${FLIGHT_API_TOKEN}"
          }
        }
      }
    }
    ```

    **Best for**: Production deployments, shared infrastructure, team-wide tools.
  </TabItem>
</Tabs>

## The Three Primitives

Every MCP server exposes capabilities through exactly three types. The key question for each: **who decides?**

### Tools — Model-Controlled

Functions the AI decides to call. This is what you'll use 90% of the time.

```python
from mcp.server import Server

server = Server("travel-flights")

@server.tool()
async def search_flights(
    origin: str,
    destination: str,
    date: str,
    passengers: int = 1
) -> str:
    """Search available flights between two airports on a given date.
    
    Args:
        origin: IATA airport code (e.g., 'CDG')
        destination: IATA airport code (e.g., 'NRT')
        date: Travel date in YYYY-MM-DD format
        passengers: Number of passengers (default: 1)
    """
    results = await flight_api.search(origin, destination, date, passengers)
    return format_flight_results(results)
```

The AI model sees the tool name, description, and parameter schema — and **decides when and how to call it**. The docstring is critical: it's the tool's user manual for the AI.

### Resources — Application-Controlled

Read-only data the AI can access. Like GET endpoints — the host decides what to include in context.

```python
@server.resource("flights://status/{flight_number}")
async def get_flight_status(flight_number: str) -> str:
    """Get real-time status of a specific flight."""
    status = await flight_api.get_status(flight_number)
    return json.dumps(status, indent=2)
```

### Prompts — User-Controlled

Reusable templates the user selects. Standardizes how the AI approaches domain-specific tasks.

```python
@server.prompt()
async def disruption_analysis(flight_number: str) -> str:
    """Analyze a flight disruption and suggest rebooking options."""
    return f"""Analyze the disruption for flight {flight_number}.
Steps:
1. Check current flight status
2. Identify affected passengers
3. Search for alternative flights
4. Rank alternatives by tier, feasibility, cost
5. Generate rebooking recommendation"""
```

<KeyInsight>
**Tools** = model-controlled (AI decides to call). **Resources** = application-controlled (host decides to include). **Prompts** = user-controlled (user selects). Three primitives, three control planes — this separation is the foundation of MCP's security model.
</KeyInsight>

## MCP in the Wild

You're probably already using MCP without knowing it.

**Claude Code** uses MCP servers for file system operations, bash execution, and web fetching. Every time Claude Code reads a file — that's MCP under the hood.

**A typical Cursor/VS Code setup:**

```json
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres"],
      "env": { "DATABASE_URL": "postgresql://localhost:5432/mydb" }
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}
```

Your editor's AI can now query your database and interact with GitHub — through a standard protocol. Want to swap the GitHub server for GitLab? The client code doesn't change.

## Hands-On: Building a Flight MCP Server

Let's build a flight information server from scratch:

```python
# flight_mcp_server.py
import json
from mcp.server import Server
from mcp.server.stdio import stdio_server

server = Server("travel-flight-tools")

FLIGHTS_DB = {
    "AF1234": {
        "carrier": "Air France", "origin": "CDG", "destination": "NRT",
        "departure": "2025-03-15T10:30:00", "status": "on_time",
        "aircraft": "A350-900", "passengers": 287
    },
    "AF5678": {
        "carrier": "Air France", "origin": "CDG", "destination": "JFK",
        "departure": "2025-03-15T14:00:00", "status": "delayed",
        "delay_minutes": 45, "aircraft": "B777-300ER", "passengers": 342
    }
}

@server.tool()
async def get_flight_status(flight_number: str) -> str:
    """Get the current status of a flight by its flight number.

    Args:
        flight_number: The flight number (e.g., 'AF1234')
    """
    flight = FLIGHTS_DB.get(flight_number.upper())
    if not flight:
        return f"Flight {flight_number} not found."
    return json.dumps({
        "flight": flight_number.upper(),
        "carrier": flight["carrier"],
        "route": f"{flight['origin']} → {flight['destination']}",
        "status": flight["status"],
        "departure": flight["departure"],
    }, indent=2)

@server.tool()
async def list_flights(origin: str = "", destination: str = "") -> str:
    """List available flights, optionally filtered by origin/destination."""
    results = []
    for fn, data in FLIGHTS_DB.items():
        if origin and data["origin"] != origin.upper():
            continue
        if destination and data["destination"] != destination.upper():
            continue
        results.append({"flight_number": fn, "route": f"{data['origin']} → {data['destination']}", "status": data["status"]})
    return json.dumps(results, indent=2) if results else "No flights found."

async def main():
    async with stdio_server() as (read_stream, write_stream):
        await server.run(read_stream, write_stream)

if __name__ == "__main__":
    import asyncio
    asyncio.run(main())
```

<DeepDive title="Advanced: Security and OAuth 2.1">

### Security Considerations

MCP introduces a new attack surface. Three defense layers:

**1. Tool Confirmation** — The host shows the user what tool is being called before executing:
```
AI wants to call: delete_booking(booking_id="ABC123")
[Allow] [Deny] [Allow All for this session]
```

**2. Scoped Permissions** — Servers implement least-privilege access.

**3. Input Validation** — Never trust tool inputs blindly. They come from the LLM, which can be manipulated via prompt injection:
```python
@server.tool()
async def query_database(sql_query: str) -> str:
    """Execute a read-only SQL query."""
    if not sql_query.strip().upper().startswith("SELECT"):
        return "Error: Only SELECT queries are allowed."
    async with read_only_pool.acquire() as conn:
        result = await conn.fetch(sql_query)
    return json.dumps(result)
```

### OAuth 2.1 for Remote Servers

Production Streamable HTTP servers integrate with existing identity providers (Active Directory, Okta) via OAuth 2.1. The client obtains an access token, then includes it as a Bearer token in MCP requests.

For full details: [modelcontextprotocol.io/docs/learn/architecture](https://modelcontextprotocol.io/docs/learn/architecture)

</DeepDive>
