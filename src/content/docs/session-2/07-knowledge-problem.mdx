## Quick Refresher: Token & Context Window

You learned these in Module 1. Two sentences is all you need:

**Tokens** are the atomic chunks an LLM reads (~4 characters each) — they drive cost, speed, and limits. The **context window** is the total token budget for a single LLM call — system prompt, retrieved docs, chat history, and the user's question must all fit inside it.

Everything in Session 2 is shaped by these two constraints. If a concept feels unfamiliar, revisit Module 1.

## The Three Blind Spots

Your agent has three fundamental knowledge gaps. No amount of prompt engineering, tool-calling, or graph orchestration can fix them. They are **architectural problems** that require an **architectural solution**.

### 1. Hallucination

The LLM doesn't "know" facts. It predicts the next token. When training data is sparse on a topic, it fills the gap with plausible fiction.

```python
# Ask about a specific internal API
response = llm("What are the rate limits for Amadeus Flight Offers v4?")
# → "The Amadeus Flight Offers v4 API allows 100 requests per minute
#    per API key, with a burst limit of 20 concurrent requests..."
#
# Sounds authoritative. Entirely fabricated.
# There is no v4. The real limits are different.
# The model can't distinguish between what it knows and what it invents.
```

### 2. Stale Knowledge

Every model has a training cutoff date. The world moves on. The model doesn't.

Your flight disruption policy changed last Tuesday. A new GDS command was added yesterday. Q3 fare rules were published this morning. The model knows **none of this**. Retraining costs GPU-weeks and six-figure budgets — that's not a workflow, it's a crisis.

### 3. Zero Access to Private Data

LLMs are trained on the public internet. They have **zero knowledge** of:

- Your GDS documentation and Cryptic commands
- Internal wikis, architecture decisions, onboarding docs
- Customer contracts and SLA terms
- Incident post-mortems and runbooks
- Yesterday's flight schedule changes

This is not a model quality problem. GPT-5 won't fix it. Claude 5 won't fix it. Your private data was never in the training set and never will be.

## RAG in 30 Seconds

**Retrieval-Augmented Generation.** Three steps. One sentence each.

1. **Retrieve** — Find the relevant documents from your knowledge base
2. **Augment** — Inject those documents into the LLM's prompt
3. **Generate** — The model answers grounded in your actual data

The model doesn't change. The input does.

```python
# RAG in 10 lines
def rag_answer(question: str) -> str:
    # 1. RETRIEVE — find relevant documents
    relevant_docs = vector_store.similarity_search(question, k=5)

    # 2. AUGMENT — inject into prompt
    context = "\n\n".join([doc.page_content for doc in relevant_docs])
    prompt = f"""Answer based ONLY on this context. If unsure, say so.

Context:
{context}

Question: {question}"""

    # 3. GENERATE — grounded answer
    return llm.invoke(prompt)
```

That's the entire pattern. Everything else — embeddings, chunking, vector stores, re-ranking — is about making each of these three steps work better.

## RAG vs Fine-Tuning

The question everyone asks. Here's the decision matrix:

| | RAG | Fine-Tuning |
|---|---|---|
| **Purpose** | Model needs to **know** something | Model needs to **behave** differently |
| **Data freshness** | Real-time (re-index anytime) | Stale (requires retraining) |
| **Source attribution** | Built-in (you know which doc) | Not possible |
| **Cost** | Low (embedding + storage) | High (GPU hours) |
| **Hallucination control** | Strong (grounded in sources) | Weak (still generates freely) |
| **Setup time** | Hours | Days to weeks |
| **Best for** | Knowledge retrieval, Q&A, search | Tone, format, domain language |
| **Travel example** | "What's the rebooking policy?" | "Always respond in GDS Cryptic format" |

## New Vocabulary: Vector, Similarity, Embedding

The RAG pseudocode above had a line you haven't seen before: `vector_store.similarity_search()`. To understand what that does, you need three new words. Just three. They power every RAG system.

### Vector — A List of Numbers

A **vector** is a list of numbers that represents meaning. That's the entire definition.

```python
vector = [0.12, -0.34, 0.87, 0.04, -0.56, 0.23, ...]
# Usually 384, 768, or 1536 numbers (depending on the model)
```

Think of it as **coordinates in meaning-space**. Just like GPS coordinates place you on a map, a vector places a piece of text on a map of meaning. Texts about the same topic land near each other. Texts about different topics land far apart.

```
                    fare rules  ●
                                          pricing  ●
        hotel booking ●
                                                   revenue  ●
                    room types  ●
                                flight delay ●
                                          cancellation  ●
```

Hotel topics cluster together. Flight disruption topics cluster together. Pricing sits between them. **Vectors turn text into coordinates so we can measure "are these about the same thing?" with simple math.**

### Similarity — How Close Are Two Vectors?

Once you have two vectors, you measure how close they are. Close = similar meaning. Far = different meaning.

The standard math is **cosine similarity** — a score between -1 and 1:

| Cosine | Meaning | Travel Example |
|---|---|---|
| **1.0** | Identical | "flight cancelled" vs "flight cancelled" |
| **0.9 -- 1.0** | Almost the same | "flight cancelled" vs "flight has been cancelled" |
| **0.7 -- 0.9** | Related, same topic | "flight cancelled" vs "rebooking options for disrupted passengers" |
| **0.4 -- 0.7** | Loosely related | "flight cancelled" vs "airline customer service hours" |
| **0.0** | Unrelated | "flight cancelled" vs "pasta recipe" |
| **< 0.0** | Opposite meaning | Rare in practice with modern embeddings |

You don't need to remember the formula. Just: **higher cosine = more similar meaning**.

When you call `vector_store.similarity_search(query, k=5)`, here's what happens:

1. Your query gets converted to a vector
2. The system computes cosine similarity against **every** vector in the store
3. It returns the **5 with the highest scores**
4. Those map back to text chunks, which get injected into the prompt

That's the entire "magic" of semantic search. No keyword matching. No SQL. Just: which stored texts are closest in meaning to this question?

<KeyInsight>
**Similarity is the math behind "find me chunks that mean the same thing."** The vector store does the computation. You just need to know what the score means: higher = more relevant.
</KeyInsight>

### Embedding — How Text Becomes a Vector

How does text turn into a list of numbers? Through an **embedding model** — a specialized model whose only job is "text in, vector out."

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer('all-MiniLM-L6-v2')

vec1 = model.encode("CDG flight delayed 3 hours")
vec2 = model.encode("Paris airport departure postponed")
vec3 = model.encode("Best hotel pools in Bali")

# vec1 and vec2 will be very close (same meaning, different words)
# vec1 and vec3 will be far apart (completely different topics)
```

The embedding model is trained so that texts with **similar meaning** produce **similar vectors**, regardless of the exact words used. "Cancelled flight" and "iptal edilen ucus" and "vol annule" can all land in the same neighborhood.

**Embedding model vs LLM — two different jobs:**

| | Embedding Model | LLM (Chat Model) |
|---|---|---|
| **Input** | Text | Text |
| **Output** | A vector (list of numbers) | Text |
| **Used for** | Search, similarity, clustering | Generation, reasoning, conversation |
| **Examples** | `text-embedding-3-small`, `all-MiniLM-L6-v2` | GPT-4o, Claude Sonnet 4, Llama 3 |
| **Cost** | Very cheap (~$0.02/M tokens) | Expensive (~$3-15/M tokens) |

In a RAG system, **you use both**: the embedding model for the search step, the LLM for the generation step. They're complementary, not competitors.

<KeyInsight>
**An embedding is what you get when you pass text through an embedding model.** Text in, vector out. That vector is the text's address in meaning-space. Two texts with similar meaning get similar addresses.
</KeyInsight>

## The Indexing Pipeline

Before RAG can answer anything, you prepare your knowledge base. This happens offline, once (and then incrementally as documents change):

<FlowDiagram title="Indexing Pipeline: Load → Chunk → Embed → Store">
  <div class="flow-row">
    <div class="flow-node secondary">
      <span class="node-icon">📄</span>
      <span class="node-label">Load</span>
      <span class="node-desc">PDF, web, markdown, API docs</span>
    </div>
    <div class="flow-arrow animated">→</div>
    <div class="flow-node secondary">
      <span class="node-icon">✂️</span>
      <span class="node-label">Chunk</span>
      <span class="node-desc">Split into focused passages</span>
    </div>
    <div class="flow-arrow animated">→</div>
    <div class="flow-node secondary">
      <span class="node-icon">🧮</span>
      <span class="node-label">Embed</span>
      <span class="node-desc">Convert each chunk to a vector</span>
    </div>
    <div class="flow-arrow animated">→</div>
    <div class="flow-node success">
      <span class="node-icon">💾</span>
      <span class="node-label">Store</span>
      <span class="node-desc">Save vectors in a vector database</span>
    </div>
  </div>
</FlowDiagram>

Each step has a job:

| Step | What It Does | Travel Example |
|---|---|---|
| **Load** | Read raw documents into memory | Load the 200-page GDS Integration Guide PDF |
| **Chunk** | Split into small, focused passages | Break it into ~500-token passages with overlap |
| **Embed** | Convert each chunk to a vector | Each passage becomes a 384-dimensional coordinate |
| **Store** | Save vectors + text in a vector database | All 400+ chunks searchable in milliseconds |

```python
from langchain_community.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.embeddings import HuggingFaceEmbeddings
from langchain_chroma import Chroma

# 1. LOAD — read documents
docs = PyPDFLoader("gds-integration-guide.pdf").load()
print(f"Loaded {len(docs)} pages")

# 2. CHUNK — split into focused passages
chunks = RecursiveCharacterTextSplitter(
    chunk_size=1000,    # ~250 words per chunk
    chunk_overlap=200   # overlap prevents cutting mid-sentence
).split_documents(docs)
print(f"Split into {len(chunks)} chunks")

# 3. EMBED + STORE — convert to vectors and save
vector_store = Chroma.from_documents(
    documents=chunks,
    embedding=HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2"),
    persist_directory="./chroma_db"
)
print(f"Indexed {len(chunks)} chunks into vector store")
```

<DeepDive title="The Academic Origins of RAG">

RAG was introduced in the 2020 paper **"Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks"** by Patrick Lewis et al. at Facebook AI Research.

The key contribution: combine a pre-trained seq2seq model (BART) with a dense retriever (DPR), trained end-to-end. The retriever and generator jointly optimize what to retrieve and how to generate.

Modern RAG has diverged significantly. Today's systems use frozen LLMs (no end-to-end training), vector databases instead of FAISS, and prompt engineering instead of fine-tuned generators. The term "RAG" has evolved from a specific architecture to a **design pattern** — any system that retrieves external knowledge to augment generation.

**Key papers in the RAG lineage:**
1. **DPR** (Karpukhin et al., 2020) — Dense Passage Retrieval
2. **RAG** (Lewis et al., 2020) — The original paper
3. **RETRO** (Borgeaud et al., 2022) — Retrieval-enhanced transformers at scale
4. **Self-RAG** (Asai et al., 2023) — LLM decides when to retrieve
5. **CRAG** (Yan et al., 2024) — Corrective RAG with retrieval evaluation

</DeepDive>

<DeepDive title="Why Not Just Use a Bigger Context Window?">

Models like Gemini offer 1M+ token context windows. Why not dump all your documents in and skip RAG entirely?

Three reasons:

1. **Cost** — Sending 500K tokens per query is extremely expensive. RAG sends only the 5 most relevant chunks (~2-5K tokens). That's a 100x cost difference.
2. **Lost in the middle** — Research shows LLMs struggle to find relevant information buried in very long contexts. They attend well to the beginning and end, but lose accuracy in the middle. RAG pre-filters so the model only sees what matters.
3. **Scale** — Your knowledge base might be 50M tokens. No context window fits that. RAG's indexing pipeline handles any size.

Big context windows are useful — but as a complement to RAG, not a replacement.

</DeepDive>

Three things to carry into the rest of Session 2:

1. **LLMs have three blind spots** — hallucination, stale knowledge, no private data access. RAG fixes all three by changing the input, not the model.

2. **RAG = Retrieve, Augment, Generate.** Find relevant docs, inject into prompt, generate a grounded answer. The model stays the same; the architecture changes everything.

3. **Three new words** — a **vector** is a list of numbers representing meaning, **similarity** measures how close two vectors are, and an **embedding** is what you get when you pass text through an embedding model. These three concepts power every line of RAG code.
